# Qualifying a Driver, ORM, or Framework with PGAdapter

This document outlines the standard process for qualifying and supporting a new driver, Object-Relational Mapper (ORM), schema management, or database framework with PGAdapter. Qualifying a framework ensures compatibility, provides references for customers, and guarantees that future PGAdapter changes do not break integrations.

---

## Qualification Overview

Qualifying a framework involves four core components:
1. **Mock Server Tests**: Verifies query rewriting, data-type compatibility, transaction handling, and client protocol interaction using an in-process, mock Spanner database server.
2. **Integration Tests**: Executes operations against a live Spanner Emulator (and/or real Spanner) to ensure end-to-end functionality.
3. **Sample Application**: A representative, runnable example of the framework connecting to PGAdapter. The sample itself runs in CI.
4. **Documentation**: Detailed guide explaining setup, driver connection strings, and any known limitations or workarounds.

### The "Time to First Surprise" (TTFS) Principle
The primary goal of qualifying a driver or ORM is to achieve a seamless drop-in experience. To verify this, **always attempt to run the framework's official "Getting Started" tutorial or "Quickstart Guide"** against PGAdapter with zero modifications to the application code. If a user can follow the official guide without encountering unexpected syntax errors or behavior ("surprises"), the qualification is successful. Any deviation from the official tutorial setup must be treated as a PGAdapter bug or documented explicitly as a known limitation.

## 1. Mock Server Tests

Mock server tests are highly robust because they execute client-driver queries against an in-process PGAdapter proxy instance communicating with an in-memory gRPC mock Spanner server (`MockSpannerServiceImpl`).

### Step A: Test Runner Script
Create a subdirectory under `src/test/<language>/<framework>-tests`.
Write a test runner script (e.g. `src/index.ts` for Node.js, `test.py` for Python, etc.) that:
- Uses a CLI library (like `yargs` or `argparse`) to accept connection parameters: `host`, `port`, `database`.
- Defines commands corresponding to each test scenario. **Ensure you cover all core features demonstrated in the framework's official "Getting Started" or "Quickstart" tutorial**. This typically includes:
  - Basic queries (`SELECT 1`, SELECT rows)
  - CRUD operations (Insert, Update, Delete) — *Note: Spanner does not allow updating primary key columns via UPDATE statements, so ensure update tests target non-primary-key columns.*
  - Parameterized query values
  - Basic relationship queries and joins
  - Transaction blocks (Read-Write and Read-Only sessions, if supported)
  - Null value handling across all supported data types
- Instantiates the client/ORM, executes the relevant query, and outputs the output directly to stdout or stderr.

### Step B: Java Test Wrapper
Create a JUnit Test Class under `src/test/java/com/google/cloud/spanner/pgadapter/<language>/<Framework>MockServerTest.java`.
- Inherit from `AbstractMockServerTest`.
- Implement parameterized testing if applicable (e.g., test both TCP port and Unix domain socket connections if supported by the driver).
- Annotate with `@Category(<Language>Test.class)` (e.g., `@Category(NodeJSTest.class)`).
- Use `mockSpanner.putStatementResult()` to pre-register statements and their expected mock results (e.g., rows, updates, errors, or custom query results).
- Call `runTest("testScenarioName", host, port)` to invoke the test runner subprocess.
- Assert stdout output of the subprocess match expectations.
- Assert mock Spanner server received the correct gRPC request payloads (e.g., correct transaction settings, commit calls, rollback calls).

## 2. Integration Tests

Integration tests run the exact same test runner script against a live Spanner emulator or real Spanner instance.

- Create a JUnit class `src/test/java/com/google/cloud/spanner/pgadapter/<language>/IT<Framework>Test.java` implementing `IntegrationTest`.
- Set up a static `PgAdapterTestEnv` instance.
- In `@BeforeClass`, invoke the driver dependency installation, initialize the emulator database tables, and start PGAdapter server.
- Write test cases that run the test runner script and verify data state directly in the Spanner database using standard Spanner Java client database assertions.
- **Verify Schema Migrations**: If the framework includes a built-in schema migration tool (e.g. Prisma Migrate, Drizzle Kit, Liquibase, Flyway, etc.):
  - Attempt to execute the automatic schema migrations against PGAdapter.
  - Assess if the DDL commands generated by the tool are fully compatible with Cloud Spanner's PostgreSQL dialect.
  - If migrations fail due to Spanner's DDL dialect constraints (which supports a smaller subset of PostgreSQL DDL compared to a real PostgreSQL instance), check if there are simple configuration workarounds.
  - If migrations cannot be used out-of-the-box or require significant workarounds, mark schema migrations as **not supported** in the documentation and detail the DDL limitations explicitly.

## 3. Sample Application

The sample application serves as user-facing documentation and acts as a CI smoke test.

### Requirements:
- Locate the sample under `samples/<language>/<framework>-sample/`.
- Must contain a `package.json`, `requirements.txt`, `go.mod`, or equivalent dependency manifest.
- Implement automatic startup of PGAdapter and the Spanner Emulator in a Docker container using **Testcontainers** (or similar library) for development and test workflows. Ensure this can be bypassed or customized via environment variables.
- Write sample code that showcases typical CRUD operations, transactions, and Spanner-specific features (such as setting session-level read staleness or executing stale reads).
- Add the sample runner to the appropriate CI workflow (e.g., `.github/workflows/samples.yaml`) to ensure it runs on every pull request.

## 4. Documentation

Documentation helps users understand how to configure and run the qualified framework.

- **README Update**: Add a row to the main `README.md` table linking to the new docs.
- **Dedicated Doc**: Create `docs/<framework>.md`.
  - Provide connection string examples showing PGAdapter configurations.
  - **Detail Known Limitations**: Document all missing SQL features, unsupported ORM APIs, or migration tool restrictions (e.g. if the ORM uses `LATERAL` joins under the hood, or if schema migrations require manual DDL statements).
  - Include code snippets demonstrating how to initialize the connection.
  - Link directly to the sample application in `samples/`.

## 5. Spanner Optimizations

When qualifying a framework, you must identify, implement, and document optimizations specific to Cloud Spanner. This ensures the integration runs efficiently and does not suffer from excessive round-trips or transaction overhead.

### A. DDL Batching
Creating or updating a database schema using separate, individual DDL statements causes high latency in Cloud Spanner.
- **Requirement**: Always group schema setup or table creation statements in your samples or test suites into a single DDL batch.
- **Implementation**: Wrap the DDL execution blocks with PGAdapter's batch boundaries:
  ```sql
  START BATCH DDL;
  ALTER DATABASE db SET spanner.default_sequence_kind='bit_reversed_positive';
  CREATE TABLE singers (...);
  CREATE TABLE albums (...);
  RUN BATCH;
  ```
  Or use driver-level native batch operations if supported.

### B. Batch DML
Executing multiple DML write/update operations individually inside a transaction incurs network round-trip overhead.
- **Requirement**: Always include a sample demonstrating how to execute multiple DML statements as a Spanner DML Batch, and verify this functionality in your integration tests.
- **Implementation**: Wrap Drizzle or other client-side DML operations inside a transaction block using session-level batch queries:
  ```typescript
  await db.transaction(async (tx) => {
    await tx.execute(sql`START BATCH DML`);
    await tx.insert(users).values({ name: 'batch-foo' });
    await tx.insert(users).values({ name: 'batch-bar' });
    await tx.execute(sql`RUN BATCH`);
  });
  ```
  Ensure integration tests assert that the mock Spanner server received exactly one `ExecuteBatchDmlRequest` containing the expected statements.

### C. ORM and Driver Native Batching Integration Points
Many client libraries, drivers, or ORMs have native batching capabilities:
- **Requirement**: Investigate if the framework has idiomatic batching patterns (such as JDBC `addBatch()` / `executeBatch()` for `Statement` and `PreparedStatement` APIs, or ORM-specific bulk managers).
- **Implementation**:
  - Prefer using these framework-native integration points in your samples.
  - PGAdapter often translates these driver-native batch calls automatically to Spanner DDL/DML batches. If supported, verify this translation behavior in your test suites.
